# 接口自动化测试框架 · 升级计划书

> 版本:v1.0(2026-10-02)
> 目标:把这个项目从"结构完整的模板"升级为"可运行、CI 全绿、面试经得起追问"的简历级开源项目。

---

## 一、背景与问题诊断

当前项目的分层架构、代码风格、工程化配套(Docker / CI / 通知)观感良好,但存在四类致命问题:

| 编号 | 问题 | 严重度 | 说明 |
|------|------|--------|------|
| P1 | **项目跑不起来** | 🔴 致命 | 所有 `base_url` 是 `example.com` 占位地址,无被测服务,测试必挂,CI 每次提交红 ✗ |
| P2 | **核心卖点未打通** | 🔴 致命 | YAML 中 `${user_id}` 无任何地方写入上下文;上下文是 function 级、用例后清空,"长链路参数传递"实际不存在 |
| P3 | **数据驱动设计反向** | 🟠 严重 | 每个测试方法全量 parametrize 后用 `pytest.skip` 过滤,用例越加越膨胀;YAML 的 `method` 字段被忽略;`UserApi` 封装层是死代码 |
| P4 | **简历口径与仓库不符** | 🟠 严重 | 项目.md 写"50+ 接口 / 200+ 用例",仓库仅 3 方法 5 用例;写"钉钉"实为飞书 |

其他细节问题:POST 请求会被自动重试(有重复下单风险)、`assert_jsonpath` 中 `${TMP_TOKEN}` 魔法字符串、业务异常用裸 `Exception`、框架自身零单测、`pytest.ini` 把 `--env=test` 写死在 addopts。

## 三、升级内容规划

### 阶段一:内置被测演示服务,让项目"能跑"(P0)

**新增 `demo_app/` 目录**——一个轻量 FastAPI 被测系统,作为框架的"靶子":

| 模块 | 接口 | 说明 |
|------|------|------|
| 用户 | `POST /api/login`、`GET/PUT /api/users/{id}` | JWT 鉴权,返回 `token`、`user_id` |
| 商品 | `GET /api/products/{id}` | 库存、在售状态 |
| 订单 | `POST /api/orders`、`GET /api/orders` | 校验库存并扣减,落库 MySQL |

技术要点:

- 统一响应包 `{code, message, data}`,业务错误 `code != 0`,与框架 `_check_response` 契合;
- 数据库复用 docker-compose 中已有的 MySQL 服务(而不是 SQLite),让"落库断言"有真实意义;
- 提供种子数据脚本(测试用户、商品),容器启动时自动初始化;
- `docker-compose.yml` 增加 `demo-app` 服务 + healthcheck,`test-runner` 的 `depends_on` 改为 `condition: service_healthy`;
- `env_config.yaml` 的 `test` 环境指向 `http://demo-app:8000`;**删除 prod 配置段**(防止误连生产,也是面试可以主动讲的安全设计点)。

### 阶段二:核心设计修复,让卖点"名副其实"(P0)

**2.1 数据驱动重构**(`core/data_driver.py`)

- `DataDriver.parametrize(data_file, feature=None, story=None)`:加载时按模块过滤,取代运行时 `pytest.skip`;
- 用例执行统一走 `request: {method, url, ...}` 分发,YAML 的 `method` 字段真正生效;
- 用例结构增加 `extract:` 段(见 2.3)与 `setup/cleanup` 钩子占位。

**2.2 API 封装层启用**(`api/`)

确立混合模式(业界主流做法,面试好讲):

- **数据驱动**负责业务参数与断言的多参数覆盖(一条方法 × N 组数据);
- **API 对象层**(`UserApi` / 新增 `OrderApi`、`ProductApi`)负责前置造数、登录鉴权、清理等流程编排;
- `conftest.py` 提供带 token 的 `auth_client` fixture,从上下文读取鉴权信息。

**2.3 上下文传递打通**(`core/context_manager.py`)

- 用例响应后按 `extract: {user_id: "$.data.user_id"}` 自动提取写入上下文;
- 上下文分级:function 级默认隔离 + session 级 `chain_context` 支撑跨用例链路(登录 → 下单);
- 渲染支持 `${key}` 与 `${context.key}`,`TestContext.render` 与 `DataDriver.render` 合并为一个实现,消除重复;
- 删除 `${TMP_TOKEN}` 魔法字符串,`expected: null` 语义明确为"仅校验字段存在";
- 链路用例用 `pytest-dependency` 或命名约定保证顺序,并对链路模块禁用随机顺序。

**2.4 健壮性细节**

- 重试策略按方法区分:仅幂等方法(GET/PUT/DELETE)自动重试,POST 默认不重试,避免重复下单;
- 业务异常改用自定义 `BusinessError(Exception)`;
- `pytest.ini` 的 `--env=test` 从 addopts 移除,环境选择只靠 `--env` 参数或 `TEST_ENV` 变量。

### 阶段三:质量自证与 CI 全绿(P1)

**3.1 框架自身单测**(新增 `unit_tests/`,marker `unit`)

| 被测对象 | 用例要点 |
|----------|----------|
| 模板渲染 | 字符串/嵌套 dict/list、未命中占位符保留原样 |
| JsonPathExtractor | 正常提取、无命中、非法表达式 |
| ConfigManager | 环境合并、环境变量注入、缺失环境报错 |
| DataManager | 结构校验、case_id 查询 |
| DatabaseHelper | 用假连接对象验证 SQL 拼装与回滚逻辑 |
| FeishuNotifier | 用 `responses`/`requests-mock` 验证签名与卡片结构 |

配套 `pytest-cov` 输出覆盖率,目标:核心工具类覆盖率 ≥ 80%。

**3.2 CI 流水线修复**(`.github/workflows/test.yml`)

- 步骤:装依赖 → 启动 MySQL(service 容器)+ uvicorn 演示服务 → wait-for-it 健康检查 → `pytest -m "unit or smoke"` → Allure 报告部署 GitHub Pages;
- README 顶部加 badge:CI 状态、Python 版本、License;
- 飞书通知附上 Allure 报告链接(CI 环境注入报告地址)。

**3.3 报告增强**

- autouse fixture:每条用例失败时自动附件化请求/响应/日志,Allure 里可直接看到参数流动证据;
- Allure `environment.properties` 写入当前环境信息。

### 阶段四:门面与简历口径(P1)

**4.1 README 重写**

- 新增架构图(Mermaid 或图片):分层 + 执行流程 + 数据流;
- 补齐"快速开始"(3 条命令跑通)、设计决策说明(为什么混合模式、为什么 POST 不重试)、测试报告截图。

**4.2 项目.md 口径修正(关键)**

- "钉钉" → "飞书"(与代码一致);
- 数字口径二选一:
  - A. 若 50+ 接口/200+ 用例来自公司内项目:文案改为"框架在公司内项目落地(内网代码),本仓库为可运行开源精简版,含 X 模块 Y 条演示链路";
  - B. 若无公司项目支撑:删除具体数字,改为可验证的表述("覆盖登录-下单-库存核心链路,支持数据驱动多参数覆盖")。
- 保留"回归时长 4h → 5min"这类相对收益描述,但需能在面试中自圆其说(口径:冒烟链路自动化替代手工回归)。

**4.3 收尾**
