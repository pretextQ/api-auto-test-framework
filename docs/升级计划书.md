## 2. 优先级定义

| 级别 | 含义 | 处理原则 |
|------|------|----------|
| P0 | 结果错误或存在明显安全问题 | 下一次发布前必须完成 |
| P1 | 影响常用执行方式或维护效率 | 近期迭代完成 |
| P2 | 体验、扩展性或工程规范改进 | 按收益排期 |

## 3. v1.2：可信与安全

### P0-1 修复演示服务越权

现状：创建订单接口接受客户端传入的 `user_id`，但没有与 Token 用户比对；用户详情接口也缺少资源归属校验。

计划：

- 创建订单时直接使用 Token 中的用户 ID；
- 用户详情接口只允许本人访问，或引入明确的管理员角色；
- 增加“为他人下单”和“读取他人资料”的权限测试；
- 对不存在用户、失效 Token、篡改 Token 增加负向用例。

验收：越权请求返回明确业务错误，且数据库中不产生记录。

### P0-2 消除用例顺序依赖

现状：查询订单依赖前置下单用例和会话级上下文，单独执行、随机顺序或并行执行时不可靠。

计划：

- 用 fixture 为每条业务测试创建独立用户态和订单数据；
- fixture teardown 按本次创建的数据主键清理，不做全表删除；
- 链路场景在一条测试或显式场景对象内完成；
- 普通业务用例保持可单独运行；
- 增加随机顺序验证，评估并引入 `pytest-xdist`。

验收：任意单条 smoke 用例可以独立执行；随机顺序连续运行三次结果一致。

### P0-3 修正通知状态计算

现状：setup/teardown error 被计入总数，却没有计入失败数，飞书可能在 CI 失败时显示“测试通过”。

计划：

- 将 failed 和 error 统一纳入失败状态；
- 在通知中分别展示断言失败、执行错误和跳过数；
- 增加 setup error、teardown error 和通知异常单元测试；
- 通知内容附带 CI 运行和 Allure 报告链接。

验收：Pytest 非零退出且存在 error 时，通知必须显示失败。

### P0-4 Allure 敏感信息脱敏

现状：请求和响应会原样写入报告，登录密码、Authorization、Token、Cookie 等可能被发布到 GitHub Pages。

计划：

- 引入递归脱敏函数，默认覆盖常见敏感字段；
- 请求头、查询参数、请求体和响应体使用同一规则；
- 允许通过配置追加业务敏感字段；
- 评估 GitHub Pages 可见性和报告保留策略。

验收：测试产物中不能检索到演示密码和完整 JWT。

## 4. v1.3：稳定与可维护

### P1-1 原子库存扣减

- 使用条件更新或行锁处理并发扣减；
- 检查受影响行数并返回库存不足；
- 增加并发下单测试，确保库存不为负数。

### P1-2 可复现依赖

- 保留面向开发者的依赖声明；
- 生成 CI 使用的锁定版本或 constraints 文件；
- 配置依赖更新机器人和定期升级验证；
- 明确支持的 Python 版本矩阵。

### P1-3 数据模型校验

- 为 YAML 用例定义显式 schema；
- 收集阶段一次性报告所有结构错误；
- 校验 method、URL、断言结构和重复 `case_id`；
- 未解析占位符默认报错，而不是把原字符串发给服务端。

### P1-4 数据库助手安全边界

- 对允许使用的表名和列名进行白名单校验；
- 明确空 conditions 的行为，禁止意外全表查询或生成非法 SQL；
- 增加连接断开重连和事务边界测试。

### P1-5 容器构建优化

- 为根目录和 `demo_app/` 增加 `.dockerignore`；
- 排除 `.git`、虚拟环境、日志、报告和缓存；
- 固定基础镜像的可追踪版本；
- 验证镜像中不包含本地产物或凭据。

## 5. v1.4：扩展能力

### P2 候选项

- 支持 schema 断言、响应时间断言和多条 JSONPath 断言；
- 提供订单、商品等独立 API 对象，降低测试代码重复；
- 支持测试数据工厂和按主键清理；
- 输出 Allure 环境信息与失败时的结构化诊断附件；
- 提供本地 pre-commit 检查和静态类型检查；
- 增加 Python 多版本 CI 矩阵；
- 添加贡献指南、变更日志和语义化版本发布流程。

性能压测、UI 自动化、gRPC、分布式调度和测试管理平台对接暂不纳入近期范围。它们应以独立场景验证价值后再引入，避免核心框架过度复杂化。

## 6. 里程碑

| 里程碑 | 范围 | 完成标准 |
|--------|------|----------|
| M1：结果可信 | P0-2、P0-3 | 用例可独立执行，通知不误报 |
| M2：安全基线 | P0-1、P0-4 | 越权用例被阻止，报告完成脱敏 |
| M3：稳定运行 | P1-1、P1-2、P1-5 | 并发库存正确，CI 与镜像可复现 |
| M4：维护提效 | P1-3、P1-4 | 配置错误提前失败，DB 边界明确 |
| M5：能力扩展 | P2 候选项 | 根据真实使用反馈选择实施 |

## 7. 每个里程碑的通用验收

1. 新行为有对应单元测试或集成测试；
2. `pytest -m unit` 通过；
3. Docker 环境中的 smoke 测试通过；
4. `git diff --check` 无格式问题；
5. README、设计说明和维护手册与实现同步；
6. CI 产物不包含凭据、Token 或不必要的个人数据。

## 8. 发布建议

- v1.2.0：完成全部 P0 项；
- v1.3.0：完成稳定性与维护性项目；
- v1.4.0：按实际需求选择扩展能力；
- 修复不改变接口行为的问题时发布补丁版本。

版本号代表已经验收的能力，不应仅按日期或文档完成度升级。
